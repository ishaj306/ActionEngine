Architecture & product strategy · v1.0 · 2026-09-01

Document → Action Engine

An action engine that refuses to guess. Every deadline, requirement, and eligibility claim is labelled, tied to its exact source text, and honest about what it could not determine.

Modular monolith FastAPI · Next.js · Postgres+pgvector Hybrid extraction Evidence-grounded 25 deliverables
FACT INFERENCE UNCERTAIN MISSING — the four states every claim carries. This is the product.
01 / STRATEGY

Executive summary

The document-intelligence market split into two camps that never meet. Enterprise IDP platforms (Textract, Azure DI, LlamaParse, Nanonets) extract structured data with high accuracy but answer "what's on the page," not "what should I do." Consumer AI assistants (Ohai.ai, Smart Calendars AI) turn documents into reminders but do so with cheerful confidence and zero traceability — they will happily invent a reminder from an ambiguous flyer.

The Document → Action Engine sits in the gap between them, and its defensible edge is epistemic honesty, not extraction quality. It produces a dependency-ordered action plan where every claim is labelled FACT / INFERENCE / UNCERTAIN / MISSING, each fact links back to the exact source region, and the system surfaces what it could not determine rather than fabricating it.

The one-sentence definition

Give it the information. It figures out what matters, what's required, what's missing, and what to do next — and it shows its evidence for every word.

What we build first: one flow, done impeccably — a scholarship/internship notice becomes an evidence-backed, dependency-ordered plan with visible confidence and an explicit "missing information" panel. Depth over breadth is the entire thesis of this document.

02 / STRATEGY

Problem definition

The problem is not a shortage of information — it's information-to-action friction. A person can read and understand a notice and still be left to manually work out nine things:

Does it apply to me?

Relevance is buried in eligibility conditions written for a general audience.

What must I do?

Actions are implied inside prose, not listed as steps.

What do I need first?

Documents, information, and approvals are scattered across paragraphs.

By when?

Absolute, relative, and windowed deadlines mixed together.

What's unclear?

Vague references ("the designated office") that the doc never resolves.

In what order?

Task B silently depends on task A completing first.

Every one of these is a small reasoning task a human does by hand, under time pressure, across many documents. The cost of a mistake is a missed deadline or an invalidated application. The engine automates the reasoning workflow — not the reading.

05 / STRATEGY

Novelty analysis — an honest one

The spec assumed "information → action" is the novelty. After research, that framing is half true and needs correcting:

Not novel in 2026

  • OCR + structured JSON extraction
  • Pulling dates/actions from a doc
  • "Upload PDF → get a checklist"
  • "Photo → calendar event"
  • Summarization of any kind

Ohai.ai and V7 Go already ship these. Do not claim them as your innovation.

Genuinely underserved

  • Per-claim FACT/INFERENCE/UNCERTAIN/MISSING labelling
  • Evidence grounding for every fact, not just fields
  • "Does this apply to me?" relevance reasoning
  • Missing/ambiguous-info detection as a first-class output
  • Cross-document contradiction & change detection
  • Dependency-ordered planning ("blocked by X")
The real innovation

Not "AI turns documents into actions." It's a document assistant that quantifies and displays its own uncertainty, grounds every claim in source evidence, and reasons about personal relevance and inter-document consistency. The trust layer is the moat — it's the one thing both competitor camps structurally lack.

06 / STRATEGY

Refined USP

Primary user

A student facing a deadline-dense, eligibility-gated notice with real consequences for getting it wrong.

Core pain

Understanding the document is easy; turning it into the correct sequence of personal actions — without missing a hidden requirement — is not.

Differentiator

Evidence-backed, uncertainty-aware action planning. It shows its work and admits its gaps.

Why they return

Documents change. Change/contradiction detection turns a one-shot analyzer into a living plan that updates itself.

Positioning statement

For students drowning in notices, Document → Action Engine is the only assistant that converts a document into a personalized, dependency-ordered plan where every claim is traceable to its source and honest about its confidence — so you can trust it enough to actually act on it.

10 / ENGINEERING

System architecture

A modular monolith, deliberately. Microservices here would be résumé-cosplay; a clean monolith with hard module boundaries is the correct senior-engineer signal for a solo/small build, and it splits later along the seams already drawn.

┌──────────────────────────────────────────────────────────┐
│  Next.js frontend  (upload · dashboard · evidence viewer) │
└───────────────┬──────────────────────────────────────────┘
                │ REST + SSE (job progress)
┌───────────────▼──────────────────────────────────────────┐
│  FastAPI app  —  MODULAR MONOLITH                         │
│                                                          │
│   auth ── documents ── ingestion ── extraction          │
│                            │           │                 │
│                       reasoning ──── action_engine          │
│                            │                             │
│                        evidence ── export (.ics/draft)   │
└───────┬──────────────────────┬───────────────┬───────────┘
        │                      │               │
   ┌────▼────┐          ┌──────▼──────┐   ┌────▼─────┐
   │ Postgres│          │ Redis +     │   │ Object   │
   │+pgvector│          │ RQ workers  │   │ store    │
   └─────────┘          └─────────────┘   └──────────┘
      state            async pipeline      raw files

Heavy work (OCR, LLM calls) runs in Redis-backed workers, not the web process. The frontend subscribes to a job stream for live per-stage progress — which doubles as the "processing" UI. Each module owns its tables and exposes a Python interface; no module reaches into another's schema.

Evolution path for scale

Extraction/OCR is the first thing to hurt under load — extract it to a worker fleet behind a queue (already the boundary). Then split reasoning (LLM-bound, cost-sensitive) so it scales and gets rate-limited independently. Postgres → read replicas; object store → S3/CDN. The monolith's seams are the future service boundaries.

11 / ENGINEERING

AI pipeline — hybrid, not "send it all to an LLM"

The single biggest architecture mistake would be one giant "summarize this" prompt. Instead, a staged pipeline where deterministic code does what code does well and the LLM is reserved for genuine reasoning — each stage typed, testable, and independently swappable.

inFile validationmagic bytes · size · type
01Ingestion & page renderPyMuPDF
02Text extraction / OCRnative text · Tesseract fallback
03Layout + structure detectionblocks · spans · coords
04Classificationembeddings + LLM tiebreak
05Information extractionLLM · strict JSON schema
06Date normalizationdateparser / duckling
07Requirement / action extractionLLM + rule validation
08Dependency graphdeterministic DAG + topo-sort
09Relevance & ambiguity reasoningLLM · profile-conditioned
10Evidence linkingfuzzy match span → offset
11Verification passLLM-judge: claim ⊆ source?
deterministic code hybrid (code + LLM) LLM reasoning

Why each tool

  • Deterministic parsers for dates — a regex/dateparser normalizes "18 September" to an ISO date reproducibly; an LLM does this non-deterministically and can drift. Code owns the arithmetic; the LLM only finds the phrase.
  • Embeddings for classification & retrieval — cheap, fast, no per-call cost, stored in pgvector.
  • LLM only for reasoning — implied actions, relevance, ambiguity: tasks with no rule-based answer.
  • The verification pass is the anti-hallucination guardrail — a second LLM call checks that every extracted claim is entailed by its cited source span. Claims that fail are demoted to UNCERTAIN or dropped. This is where the "refuses to guess" promise is enforced mechanically, mirroring the citation-grounding pattern from current research.
12 / ENGINEERING

Data model

The structured internal representation is the point — the product must never depend on a single blob of AI text. Core entities and relationships:

User ──1:N── Document ──1:N── DocumentVersion
                              │
                              ├─1:N─ DocumentChunk ──1:N── Embedding(vector)
                              ├─1:N─ ExtractedFact ──N:1── Evidence ──N:1── DocumentChunk
                              ├─1:N─ Deadline      ─┐
                              ├─1:N─ Requirement   ─┼─ each ──1:1── Evidence
                              ├─1:N─ Action        ─┘        (page + char span)
                              ├─1:N─ Ambiguity
                              └─1:N─ ProcessingJob (stage timings, cost)

Action ──N:N── Action        (Dependency: blocks / blocked_by)
Action ──1:0..1── Task        (user-facing, completion state)
Workflow ──N:N── Document     (multi-doc, V3)
DocumentComparison ──(v1,v2)  (change detection, V3)

Every extraction-derived row (Deadline, Requirement, Action, ExtractedFact) carries a classification enum and a confidence float, and points at exactly one Evidence record. That's the invariant the whole UI leans on.

13 / ENGINEERING

Database schema

-- the epistemic enum that defines the product
CREATE TYPE claim_class AS ENUM ('FACT','INFERENCE','UNCERTAIN','MISSING');

CREATE TABLE documents (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id       uuid NOT NULL REFERENCES users(id),
  filename      text NOT NULL,
  mime_type     text NOT NULL,
  storage_key   text NOT NULL,          -- object store
  doc_type      text,                       -- notice|form|jd|policy
  status        text NOT NULL DEFAULT 'pending',
  created_at    timestamptz DEFAULT now(),
  deleted_at    timestamptz                 -- soft delete / retention
);

CREATE TABLE document_chunks (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  document_id uuid REFERENCES documents(id) ON DELETE CASCADE,
  page        int  NOT NULL,
  char_start  int  NOT NULL,
  char_end    int  NOT NULL,
  text        text NOT NULL,
  bbox        jsonb,                        -- [x0,y0,x1,y1] for highlight
  embedding   vector(768)                   -- pgvector
);

CREATE TABLE actions (
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  document_id  uuid REFERENCES documents(id) ON DELETE CASCADE,
  verb         text NOT NULL,           -- submit|collect|contact|...
  description  text NOT NULL,
  classification claim_class NOT NULL,
  confidence   real NOT NULL CHECK (confidence BETWEEN 0 AND 1),
  priority     text,                        -- critical|high|medium|low
  evidence_id  uuid REFERENCES evidence(id),
  deadline_id  uuid REFERENCES deadlines(id)
);

CREATE TABLE action_dependencies (
  action_id   uuid REFERENCES actions(id) ON DELETE CASCADE,
  depends_on  uuid REFERENCES actions(id) ON DELETE CASCADE,
  PRIMARY KEY (action_id, depends_on)
);

Indexing & vectors

  • documents(user_id, created_at DESC) — dashboard list.
  • *(document_id) on every child table — the hot join path.
  • document_chunks USING hnsw (embedding vector_cosine_ops) — semantic retrieval, one database, no separate vector store at this scale.
  • Partial index WHERE deleted_at IS NULL for the live working set.

15 / ENGINEERING

Frontend architecture

  • Next.js (App Router) + TypeScript + Tailwind. Server components for the document list; client components for the interactive evidence viewer.
  • State: TanStack Query for server state + SSE subscription for job progress. No heavyweight global store needed.
  • Evidence viewer is the crown jewel component: renders the PDF page (pdf.js), overlays highlight rectangles from bbox, and two-way-binds a claim chip ↔ its source region. Clicking "why?" scrolls + flashes the span.
  • Design system: the four claim_class values map to four reusable <Tag> variants — the same motif used throughout this document. Confidence shown as a number and a bar (never color alone → accessibility).
  • Rendering states are first-class: empty (sample docs), uploading, per-stage processing, partial-result, error-with-retry.

17 / ENGINEERING

Security & privacy architecture

Transport & storage

TLS everywhere; files encrypted at rest in object store; DB encryption at rest. Signed, expiring URLs for file access.

File handling

Magic-byte + MIME validation, size caps, render in a sandboxed worker, strip active content. Optional AV scan hook (ClamAV) before processing.

AuthN / AuthZ

Session or JWT auth; every query scoped by user_id; row-level ownership checks on every document route.

Retention

Soft-delete + user-triggered hard-delete; configurable auto-purge; "delete everything" honored across DB + object store + derived rows.

Audit & secrets

Append-only audit log of access/export/delete; secrets in env/manager, never in code; least-privilege service creds.

External-AI boundary

Explicit consent before any content leaves for an LLM API; PII-heavy docs can run redaction first; never used for training. A local-model path is the privacy escape hatch.

The key data question

Decide per-deployment what may reach an external LLM. Default: send extracted text chunks, not raw files; offer a fully-local pipeline (Tesseract + open-weights model) as the privacy tier. Document this boundary explicitly — it's both a safety control and a portfolio talking point.

18 / RIGOR

Evaluation methodology

This is what separates the project from a demo. Build a small annotated benchmark (40–60 documents: college/scholarship/internship notices, gov forms, JDs, policies, event notices). Annotate deadlines, actions, requirements, entities, ambiguities, dependencies.

Extraction metrics

  • Deadline extraction accuracy (exact-date match)
  • Action precision / recall / F1
  • Requirement extraction F1
  • Hallucination rate — claims not entailed by source
  • Evidence-attribution accuracy — cited span actually supports the claim

System & user metrics

  • Processing latency p50/p95 by document type
  • Processing success rate
  • Ablation: rule-based vs LLM-only vs hybrid
  • User study: time-to-understand, time-to-identify-actions, task completion, confidence, NASA-TLX workload
The headline experiment

The rule-vs-LLM-vs-hybrid ablation is the research spine. It lets you claim, with numbers, that the hybrid design beats either pure approach — the difference between "I built an app" and "I engineered and evaluated a system."

19 / PRODUCT

MVP definition

Tighter than the spec's §25. One flow, one user, done impeccably.

In

PDF + image upload · native text + OCR · classification · deadline / requirement / action extraction · epistemic labels · per-claim evidence · missing-info detection · checklist + completion.

Out (deferred)

Relevance profile → V2 · dependency ordering → V2 · change detection → V3 · multi-doc → V3 · live integrations → cut.

Done means

Upload a real scholarship notice → correct, evidence-linked plan with an honest missing-info panel → benchmark numbers on 40+ docs.

Discipline

The temptation is to add relevance + dependencies + comparison to the MVP because they're the exciting parts. Don't. A flawless evidence-and-honesty core on one document type is more impressive — and more shippable — than four half-features. Depth over count.

21 / RIGOR

Testing strategy

  • Unit — deterministic stages (date parsing, chunking, DAG topo-sort, dependency cycles) are pure functions → exhaustive table-driven tests.
  • Contract / schema — every LLM stage validated against a Pydantic schema; malformed output triggers a repair-retry, tested with recorded bad responses.
  • Golden-file — the benchmark corpus doubles as regression tests; extraction changes diff against annotated expectations.
  • LLM evaluation — precision/recall/hallucination tracked in CI on a fixed subset; a regression in hallucination rate fails the build.
  • Integration & E2E — upload→result API tests; Playwright for the evidence-viewer interaction.
  • Fixtures — a small set of hand-built PDFs (native, scanned, multi-column, ambiguous) covering the tricky paths.
22 / RIGOR

Deployment strategy

  • Containerized — one image, two entrypoints (web + worker); docker-compose for local (app · worker · Postgres+pgvector · Redis · MinIO).
  • Hosting — frontend on Vercel; API + workers on a container host (Fly.io / Render / Railway); managed Postgres; managed Redis. All within a student budget.
  • Config — 12-factor env vars; secrets in the platform manager; separate staging.
  • Migrations — Alembic, run on deploy; never hand-edit prod schema.
  • Observability — structured logs, per-stage timing + token cost, Sentry for errors, a simple metrics dashboard.
